# 工具契约设计：描述、参数、幂等、超时、重试与返回结构

> 目标：把“一个函数能被调用”提升为“模型、Agent Runtime 和工具服务能够安全协作的稳定协议”。示例采用 JSON Schema 2020-12，并兼顾 MCP `tools/call` 与普通 HTTP API。

## 一、工具契约不是函数签名

Agent 调用工具至少经过四层：模型根据描述选择工具，Runtime 校验并路由，工具服务执行，Runtime 再把结果转成 observation。契约必须同时服务这四层：

| 层次 | 关心的问题 | 契约缺失的后果 |
|---|---|---|
| 模型 | 何时调用、参数是什么意思、有什么副作用 | 选错工具、虚构枚举值、重复执行 |
| Runtime | 能否授权、怎样校验、何时超时和重试 | 越权、错误重试、调用悬挂 |
| 工具服务 | 请求是否唯一、结果是否已提交 | 重复扣款、状态不一致 |
| 观察与审计 | 哪些成功、哪些失败、是否可恢复 | 模型误判完成，人工无法追踪 |

因此，成熟工具契约应由六部分组成：语义描述、输入 Schema、执行语义、可靠性策略、返回 Schema、安全与审计元数据。

## 二、工具描述：写决策规则，不写营销文案

一个可用的描述至少回答：

1. **动作和对象**：到底读取、创建、修改还是删除什么；
2. **适用条件**：模型在什么用户意图下应选择它；
3. **前置条件**：认证、资源状态、必需上下文；
4. **副作用**：是否扣费、发消息、写数据库、触发异步任务；
5. **确认要求**：不可逆或对外行为是否必须先获得用户确认；
6. **时效与一致性**：返回实时值还是缓存值，写入何时可见；
7. **失败与补救**：常见业务失败，以及是否可安全重试。

```json
{
  "name": "create_refund",
  "title": "创建退款",
  "description": "为一笔已结算付款创建全部或部分退款。该操作会产生资金副作用；调用前必须取得用户对金额和原因的确认。同一退款意图重试时必须复用 idempotency_key。付款不存在、可退金额不足属于业务失败，不应自动重试。",
  "inputSchema": {},
  "outputSchema": {}
}
```

描述不是授权。即使模型正确选中工具，Runtime 和服务端仍必须检查用户、Agent、Scope、租户、资源归属和参数策略。来自第三方 MCP Server 的工具描述与 annotations 也是不可信输入，不能直接当作安全策略。

## 三、参数：枚举、默认值与条件约束

### 3.1 完整输入 Schema

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["payment_id", "amount", "currency", "reason", "idempotency_key"],
  "additionalProperties": false,
  "properties": {
    "payment_id": {"type": "string", "pattern": "^pay_[A-Za-z0-9]{12,}$"},
    "amount": {"type": "string", "pattern": "^(0|[1-9][0-9]*)\\.[0-9]{2}$"},
    "currency": {"type": "string", "enum": ["CNY", "USD", "EUR"]},
    "reason": {
      "type": "string",
      "enum": ["duplicate", "fraudulent", "requested_by_customer"]
    },
    "notify_customer": {
      "type": "boolean",
      "default": true,
      "description": "省略时由服务端按 true 处理；响应会回显 effective_parameters"
    },
    "idempotency_key": {"type": "string", "minLength": 16, "maxLength": 128}
  }
}
```

关键设计理由：

- 金额用十进制定点字符串而不是二进制浮点数，避免 `0.1 + 0.2` 类精度问题；货币仍需约束小数位和上下限。
- 枚举值使用稳定机器标识，展示文本可以本地化。枚举区分大小写；未知值应校验失败，不能静默映射。
- 对象默认设置 `additionalProperties: false`，尽早发现模型拼错字段或客户端与服务端版本漂移。
- 只有真正必填的字段放入 `required`。`null`、缺失与空字符串是三种不同语义，不应混用。
- 条件约束用 `oneOf`、`if/then/else` 或判别字段表达；不要只写在 description 中让模型“自觉遵守”。

### 3.2 `default` 最容易被误解

JSON Schema 的 `default` 是注解，不保证校验器自动填值。契约必须明确默认值由谁应用：

- 推荐由服务端定义并应用，避免不同 SDK 得到不同结果；
- 服务端在响应的 `effective_parameters` 中回显实际采用值；
- 默认值变更属于行为变更。若会改变副作用，应版本化，而不是悄悄修改；
- 时间、区域、当前用户等上下文相关值，不应伪装成静态 Schema 默认值。

## 四、幂等键：给“业务意图”编号

Trace ID 用于追踪一次链路，请求 ID 用于识别一次传输；**幂等键用于识别同一个有副作用的业务意图**，三者不能互换。

正确算法：

1. Agent 在确定“创建这笔退款”的意图边界时生成幂等键；
2. 网络超时、连接重置、令牌刷新后的同一意图重试，复用该键；
3. 服务端以 `(调用者/租户, 工具名, idempotency_key)` 建立唯一记录；
4. 首次请求保存请求指纹和最终结果；并发重复请求等待或返回 `in_progress`；
5. 相同键、相同指纹返回原结果；相同键、不同参数返回 `IDEMPOTENCY_CONFLICT`；
6. 服务端公开保存期限。过期后不能继续承诺去重，长任务还需提供状态查询接口。

客户端收到超时时，状态是“未知”，不是“失败”。此时应先用幂等键重试或查询，而不是生成新键。取消请求也只表示客户端不再等待，不代表远端事务已经回滚。

## 五、超时：使用 Deadline，而不是一个模糊秒数

一次工具调用通常包含排队、连接、读取、服务端执行和下游调用。只设置 socket timeout 无法控制总时长。应定义：

| 预算 | 含义 |
|---|---|
| 总 Deadline | Agent 本步骤最晚完成时间，建议用绝对时间或单调时钟计算剩余量 |
| 连接超时 | DNS/TCP/TLS/连接池等待上限 |
| 首字节/空闲超时 | 服务端多久必须开始响应；流式期间最大无事件间隔 |
| 服务端执行 Deadline | 工具必须停止或转为异步任务的时间 |
| 下游预算 | 从剩余 Deadline 中预留返回和清理时间后再传递 |

服务端超时分为软取消和硬终止。软取消通过 cancellation token 请求协作停止；若动作已提交，则必须返回已发生的 effects 或提供状态查询/补偿操作。不要用“客户端连接断开”推断数据库事务必然未提交。

## 六、重试：先判断失败类别，再判断副作用

推荐条件是：`可恢复错误 AND 仍在总 Deadline 内 AND 尝试次数未超限 AND 调用可安全重放`。

| 情况 | 默认策略 |
|---|---|
| 连接失败、502/503、限流 | 指数退避 + full jitter；尊重 `Retry-After` |
| 参数无效、余额不足、权限不足 | 不重试；修改输入、权限或用户决策后才是新意图 |
| Access Token 过期 | 刷新/重新交换一次；原调用只有具备幂等保证时才重放 |
| 写操作响应超时 | 复用幂等键重试或查询状态，绝不盲目换键 |
| 部分成功 | 只重试明确失败且未提交的子项；避免重放整个批次 |

退避示例：`sleep = random(0, min(cap, base × 2^attempt))`。还应同时限制最大尝试次数与最大总时长，避免多个 Agent 形成重试风暴。熔断器保护依赖服务，但不替代单次调用的超时与幂等。

## 七、统一返回结构：协议错误与业务结果分层

MCP/JSON-RPC 外层负责消息是否可解析、方法是否存在等协议问题；内层工具结果表达执行语义。MCP 建议把未知方法或畸形请求作为 JSON-RPC error，把工具执行失败作为正常 `tools/call` result 并设置 `isError: true`，这样模型可以读取可操作的错误内容。

```json
{
  "status": "success | business_failure | system_failure | partial_success",
  "data": {},
  "error": null,
  "warnings": [],
  "effects": [],
  "retry": {"retryable": false, "after_ms": null},
  "meta": {
    "request_id": "req_...",
    "trace_id": "tr_...",
    "idempotency_key": "idem_...",
    "started_at": "2026-08-10T10:00:00Z",
    "finished_at": "2026-08-10T10:00:01Z",
    "effective_parameters": {}
  }
}
```

四种状态的精确定义：

### 7.1 成功

```json
{"status":"success","data":{"refund_id":"re_123","state":"succeeded"},"error":null,
 "effects":[{"type":"refund_created","resource_id":"re_123","committed":true}],
 "retry":{"retryable":false,"after_ms":null},"meta":{"trace_id":"tr_1"}}
```

成功表示契约承诺的完成条件已经满足，而不只是“请求已接收”。异步动作应返回 task/job 句柄和 `accepted` 状态，不应伪装成最终成功。

### 7.2 业务失败

```json
{"status":"business_failure","data":null,
 "error":{"code":"INSUFFICIENT_REFUNDABLE_AMOUNT","message":"可退金额不足","details":{"available":"20.00"}},
 "effects":[],"retry":{"retryable":false,"after_ms":null},"meta":{"trace_id":"tr_2"}}
```

请求在技术上成功到达并被理解，但领域规则拒绝执行。错误码必须稳定、可机读；message 面向人，不能让模型解析自然语言判断类别。

### 7.3 系统失败

```json
{"status":"system_failure","data":null,
 "error":{"code":"DEPENDENCY_UNAVAILABLE","message":"支付网关暂不可用","details":{"execution_state":"not_started"}},
 "effects":[],"retry":{"retryable":true,"after_ms":1200},"meta":{"trace_id":"tr_3"}}
```

必须说明执行状态是 `not_started`、`committed` 还是 `unknown`。只有 `retryable: true` 不足以授权重试；Runtime 仍需检查幂等性、Deadline 和尝试预算。

### 7.4 部分成功

```json
{"status":"partial_success","data":{"items":[
   {"item_id":"a","status":"success","resource_id":"re_a"},
   {"item_id":"b","status":"business_failure","error":{"code":"ALREADY_REFUNDED"}}
 ]},"error":{"code":"BATCH_PARTIALLY_APPLIED","message":"2 项中 1 项成功"},
 "effects":[{"type":"refund_created","resource_id":"re_a","committed":true}],
 "retry":{"retryable":false,"after_ms":null},"meta":{"trace_id":"tr_4"}}
```

部分成功不是带 warning 的成功。它必须列出每个子项、已提交副作用和可单独重试集合。若业务要求全有或全无，应通过事务实现并只返回成功/失败，而不是让客户端猜测原子性。

## 八、落地检查表

- 描述明确使用条件、副作用、确认、权限和一致性；
- 输入、输出均有 Schema，服务端再次校验；
- 枚举稳定且严格，默认值的应用方和版本语义清楚；
- 写操作使用业务幂等键，并处理相同键不同参数；
- Deadline 跨层传播，取消与回滚语义分开；
- 重试由错误类别、幂等性、预算共同决定；
- 四类结果互斥，错误码稳定，部分成功列明子项与 effects；
- Trace ID、请求 ID、幂等键各司其职，敏感参数不写入日志。
