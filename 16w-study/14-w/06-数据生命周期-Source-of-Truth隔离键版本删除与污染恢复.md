# 数据生命周期：原始消息、运行状态、长期记忆、检索证据与缓存的 Source of Truth、隔离键、版本、删除与污染恢复

> 目标：为 Agent 系统里五类数据各定义六个维度——Source of Truth、生命周期、隔离键、版本、删除、污染恢复。核心是**每一类数据的「权威来源」和「谁能改、何时失效、出错怎么恢复」都不同**，混在一起就会出污染、隐私和一致性问题。

---

## 1. 阅读前术语表

| 术语 | 说明 |
|---|---|
| Source of Truth（SOT） | 某类数据的**权威存储**，其他副本都从这里派生 |
| 生命周期（Lifecycle） | 数据从创建到删除的时间线（TTL、何时失效） |
| 隔离键（Isolation Key） | 把数据分到不同「桶」的键，防止跨租户/跨会话串数据 |
| 版本（Version） | 数据 schema / prompt / 模型版本的版本号 |
| 删除（Deletion） | 用户请求删除/合规要求下，如何真正删干净 |
| 污染恢复（Pollution Recovery） | 错误数据混入后，如何定位并清除/回滚 |

---

## 2. 五类数据 × 六维度总表

| 数据 | Source of Truth | 生命周期 | 隔离键 | 版本 | 删除 | 污染恢复 |
|---|---|---|---|---|---|---|
| **原始消息** | 消息日志（append-only） | 永久/按保留期 | `user_id + session_id` | prompt/schema 版本 | 用户删除请求 → 级联 | 不可变，靠「重放正确前缀」重建 |
| **运行状态** | 运行存储（当前 run） | 短（run 结束即归档/清除） | `run_id` | run 快照版本 | run 结束自动清 | 重置/重跑该 run |
| **长期记忆** | 记忆库（经筛选的事实） | 长（显式删除或过期） | `user_id + 记忆类型` | 记忆 schema 版本 | 用户删除请求 → 逐条删 | 逐条纠错/降权/重写 |
| **检索证据** | 源文档（外部） | 短（run 内引用，事后可溯源） | `run_id + doc_id` | 源文档版本/快照 | 引用失效即弃 | 换源重检、证据溯源 |
| **缓存** | 派生自上游（非权威） | 短（TTL/失效键） | `隔离键 + 缓存键` | 上游版本戳 | 失效/清空即可 | 直接失效重建 |

下面逐类展开，重点讲**权威性**和**出错怎么恢复**。

---

## 3. 逐类详解

### 3.1 原始消息（Raw Messages）

- **SOT**：**append-only 消息日志**——用户消息、模型回复、工具调用与结果的原始记录。它是不可变的「事实」，后续的摘要/记忆/缓存都从这里派生。
- **生命周期**：按合规保留期永久留存（审计、重放、用户维权）。
- **隔离键**：`user_id + session_id`（会话内再按 `turn_id` 排序），**严禁跨用户**。
- **版本**：记录每条消息产生时的 prompt 版本、模型版本、schema 版本——否则事后无法还原「当时是什么配置」。
- **删除**：用户行使删除权（GDPR 被遗忘权）→ 从消息日志级联删除派生的摘要/记忆；删除要**可证明**（审计留痕）。
- **污染恢复**：原始消息**不可变**，所以「污染」不是改它，而是下游派生错了——恢复手段是**从正确的消息前缀重新派生**（重放），而不是去改日志。

### 3.2 运行状态（Run State）

- **SOT**：**当前 run 的运行存储**——正在进行的步骤、scratchpad、已完成的子任务、中间结果。它是「临时工作区」，不是权威知识。
- **生命周期**：**最短**——run 结束即归档（保留用于审计）或清除；崩溃时靠快照恢复。
- **隔离键**：`run_id`（一个任务一次运行一个桶）；并发子任务再加 `subtask_id`。
- **版本**：run 快照带版本，崩溃恢复时按版本回滚到最近一致点。
- **删除**：run 结束自动清，或用户中断时立即丢弃未完成状态。
- **污染恢复**：运行状态出错（坏掉一个中间步骤）→ **重置该 run 重跑**，或从最近快照回滚；它本就不该被长期信任。

### 3.3 长期记忆（Long-term Memory）

- **SOT**：**记忆库**——从原始消息里**筛选/蒸馏**出的、值得跨会话复用的事实与偏好（如「用户偏好中文回答」）。注意：它是「派生」的，原始消息才是更底层的真相。
- **生命周期**：**长**，直到显式删除或按策略过期；会随新证据**更新/覆盖**。
- **隔离键**：`user_id + 记忆类型`（偏好/事实/约束分开），**绝不跨用户共享**。
- **版本**：记忆条目带 schema 版本（新增字段时做迁移）；记录「来源消息 id」以便溯源。
- **删除**：用户删除请求 → 逐条删对应记忆，并**级联**使依赖它的缓存失效。
- **污染恢复**：这是**最需要污染恢复**的一类——一条错误记忆（如记错了用户偏好）会被反复召回、放大错误。恢复手段：**逐条纠错/降权/重写**，并记录污染来源（哪条消息导致的）以阻断再污染。第 14 周编码实验的「记忆污染回归」正是测这个。

### 3.4 检索证据（Retrieval Evidence）

- **SOT**：**外部源文档**——检索到的 chunk 只是源文档的**快照/引用**，权威在源头，不在 chunk。
- **生命周期**：**短**——只在 run 内作为证据引用；run 结束后保留的是「引用了哪个 doc/版本」而非 chunk 本身（避免陈旧）。
- **隔离键**：`run_id + doc_id`（+ 版本），跨 run 不复用（源可能已变）。
- **版本**：**源文档版本/快照**是关键——同一 doc 不同版本内容不同，引用必须带版本。
- **删除**：源文档被删/更新 → 旧引用失效；证据本身不承担长期存储。
- **污染恢复**：检索到**错误/过期/被污染的文档**（如被篡改的网页）→ 换源重检、按版本回退、对可疑源做可信度标记。这是「幻觉」的一个源头——检索证据污染 → 模型据以生成错误答案。

### 3.5 缓存（Cache）

- **SOT**：**无权威性，纯派生**——缓存永远是上游（模型输出/KV/检索结果）的副本，源头变了缓存就失效。绝不能用缓存当真相。
- **生命周期**：**短**，靠 TTL 或失效键（上游版本戳变了就失效）。
- **隔离键**：`上游隔离键 + 缓存键`——例如 prompt cache 按「规范化 prompt」、语义缓存按「用户 + query」、结果缓存按「完整 prompt」、KV cache 按「前缀」。
- **版本**：缓存条目打上**上游版本戳**（模型版本、prompt 版本、源文档版本），版本不匹配即失效。
- **删除**：缓存删除最简单——**失效/清空**即可，因为总能从上游重建。但要注意**正确性边界**（承接 13-w/06）：语义缓存/结果缓存在非确定性或依赖外部状态时**不该被缓存**，否则删不删都会错。
- **污染恢复**：缓存被污染（缓存了错误结果/KV）→ **失效重建**，从上游重新算。恢复成本最低，前提是**能识别污染**（靠版本戳/失效键）。

---

## 4. 统一判据：权威性由高到低

五类数据的权威性排个序，决定了「出错怎么恢复」：

```text
原始消息（不可变事实）
   └─ 长期记忆（筛选后的派生事实，可纠错）
        └─ 检索证据（外部源快照，可换源重检）
             └─ 运行状态（临时工作区，可重置重跑）
                  └─ 缓存（纯派生，失效重建）
```

- **越靠上越「权威、不可轻易改」**：原始消息不可变，恢复靠「重放正确前缀」；记忆可纠错但要记录来源；证据可换源但要带版本。
- **越靠下越「可弃、可从上游重建」**：运行状态可重跑，缓存可失效重建。
- **污染恢复的共同原则**：**追溯污染来源 → 阻断再进入 → 从权威源重建/纠错**，而不是就地篡改派生数据。

---

## 5. 本文结论

五类数据的关键差异在**权威性**：原始消息是**不可变事实**（SOT），长期记忆是**可纠错的派生事实**，检索证据是**带版本的源快照**，运行状态是**临时工作区**，缓存是**纯派生、可弃**。六个维度里最要紧的两个是 **Source of Truth**（谁说了算）和 **污染恢复**（错了怎么救）：SOT 决定「从哪重建」，污染恢复决定「能不能救回来」。设计任何 Agent 存储时，先回答「这类数据的权威在哪、失效怎么删、污染怎么恢复」，才不会把缓存当真相、把运行状态当记忆、把错误记忆反复召回放大。
