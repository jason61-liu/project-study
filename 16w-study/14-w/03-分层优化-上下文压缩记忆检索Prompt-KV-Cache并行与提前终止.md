# 分层优化：上下文选择/压缩、记忆检索、Prompt Cache、KV Cache、并行工具与提前终止

> 目标：把六个优化手段**按它们所在的层**摆清——上下文层、记忆层、服务层、编排层、控制流层。核心认识是：它们**不在同一层、不互相替代、各治各的病**，选哪个取决于 Trace 诊断出的瓶颈在哪。

---

## 1. 阅读前术语表

| 术语 | 说明 |
|---|---|
| 上下文选择/压缩 | 只把相关历史喂给模型、把长内容压成摘要 |
| 记忆检索 | 从长期记忆库按相关性取回历史事实/偏好 |
| Prompt Cache | 服务层复用共享前缀的 KV，跳过重复 prefill |
| KV Cache | 模型推理层缓存的 Key/Value，分页/前缀复用 |
| 并行工具 | 对无依赖的工具调用并发执行 |
| 提前终止 | 检测到循环/不收敛/已完成时提前停 |
| 层（Layer） | 系统栈的抽象层次，各层优化不同资源 |

---

## 2. 六种优化位于五个层

| 层 | 优化手段 | 治什么病 | 减少的资源 |
|---|---|---|---|
| **上下文层（应用）** | 上下文选择/压缩 | 上下文膨胀（文档 02） | 输入 token、注意力稀释 |
| **记忆层（应用）** | 记忆检索 | 重复查、跨会话遗忘 | 检索次数、重复计算 |
| **服务层（引擎）** | Prompt Cache | 共享前缀重复 prefill | prefill 算力、TTFT |
| **服务层（引擎）** | KV Cache（分页/前缀） | KV 显存、前缀复用 | 显存、prefill |
| **编排层** | 并行工具 | 串行依赖（文档 01） | 墙钟时间 |
| **控制流层** | 提前终止 | 无效反思/死循环（文档 02） | 无效模型调用 |

---

## 3. 逐层展开

### 3.1 上下文层：选择/压缩

**治的是「发太多无关 token」**。手段两条：**选择**（只保留当前任务相关的历史片段、丢弃失败尝试、工具输出只留结论）+ **压缩**（把长工具输出/检索原文压成摘要，保留关键事实与引用）。收益是输入 token 下降 → prefill 变快、注意力更聚焦、prompt cache 更容易命中。代价是压缩可能丢细节，需保留可追溯的引用。

### 3.2 记忆层：检索

**治的是「跨轮/跨会话重复查、忘掉已知事实」**。用一个长期记忆库（如 Mem0 这类 memory 层），把用户偏好、历史结论、已知约束沉淀下来，新任务先检索相关记忆再干活。收益是避免重复检索与重复推理。代价是记忆会「污染」——错误记忆被反复召回会放大错误（见文档 06 的污染恢复）。

### 3.3 服务层：Prompt Cache 与 KV Cache

**治的是「同一前缀反复 prefill、KV 显存爆」**（承接 12-w/01–04）。

- **Prompt Cache（前缀缓存）**：多个请求共享 system prompt / few-shot / 多轮历史时，复用前缀的 KV，跳过重复 prefill。命中粒度是块（vLLM）或 token（SGLang）。
- **KV Cache**：更底层——PagedAttention 分页管理、FP8 量化省显存、跨实例分层（LMCache）。

两者都是**引擎/服务层**，与应用逻辑无关，是「怎么存 KV、怎么复用」的问题。

### 3.4 编排层：并行工具

**治的是「无依赖步骤串行等」**。两个工具调用若**没有数据依赖**（A 的输入不来自 B 的输出），就该并发执行而非顺序执行。收益是把串行墙钟压成「最长单个工具」的墙钟。代价是并发要处理结果聚合、部分失败、以及「误判依赖」的风险——有依赖的工具并行会出乱序错误。

### 3.5 控制流层：提前终止

**治的是「该停不停」**。三类：**循环检测**（重复输出同一内容 → 停）、**收敛检测**（反思/优化不再改进 → 停）、**完成检测**（目标已达成 → 不再加步骤）。收益是砍掉无效模型调用（文档 02 的无效反思）。代价是提前停可能误杀「看似重复实则必要」的步骤，需保守阈值。

---

## 4. 为什么「分层」是重点

这六种优化经常被混在一起讨论，但它们**解决不同资源、作用于不同层次**：

- 上下文压缩和记忆检索是**应用层**——减的是「发给模型的 token / 检索次数」，跟引擎无关；
- Prompt/KV Cache 是**服务层**——减的是「重复 prefill 算力 / KV 显存」，跟应用逻辑无关；
- 并行工具是**编排层**——减的是「墙钟等待」；
- 提前终止是**控制流层**——减的是「无效步骤」。

**选型顺序**（和文档 01 的诊断闭环）：

```text
Trace 诊断瓶颈在哪一层 → 就在哪一层对症下药
模型 token 多 → 上下文层（选择/压缩）
重复 prefill → 服务层（Prompt Cache）
KV 显存爆 → 服务层（KV Cache/量化）
串行等待 → 编排层（并行）
无效循环 → 控制流层（提前终止）
```

**不能拿一层的东西治另一层的病**：比如 KV Cache 优化得再好，也治不了「上下文膨胀」——因为膨胀是应用层多发了无关 token，KV Cache 只能让「重复的前缀」省 prefill，救不了「每次都塞满无关历史」的 token 成本。反过来，上下文压缩也替代不了 prompt cache——压缩后前缀变了，cache 反而难命中。**各层正交、需组合使用**。

---

## 5. 组合示例：一次完整优化

一个多轮 Agent：**上下文层**压缩历史 + 丢弃失败中间过程 → **记忆层**把用户偏好存进长期记忆、跨会话复用 → **服务层**开 Prompt Cache（共享 system prompt 前缀）+ KV Cache FP8 省显存 → **编排层**把互不依赖的检索与工具并行 → **控制流层**对反思加 2 轮上限 + 循环检测。六者叠加，各管一段，缺一不可。

---

## 6. 本文结论

六个优化手段分属**五个层**：上下文选择/压缩（应用）、记忆检索（应用）、Prompt Cache + KV Cache（服务/引擎）、并行工具（编排）、提前终止（控制流）。它们**正交、不替代、各治各病**，选哪个取决于 Trace 诊断出的瓶颈所在层。记住两句话：**「发多少 token」是应用层的事，「省不省 prefill/显存」是服务层的事，「等不等」是编排层的事，「停不停」是控制流层的事**——别拿 KV Cache 去治上下文膨胀。
