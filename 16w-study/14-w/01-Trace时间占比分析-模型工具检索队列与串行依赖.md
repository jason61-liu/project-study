# Trace 时间占比：模型、工具、检索、队列与串行依赖

> 目标：从「单次模型调用」的视角切换到「端到端任务」的视角——用 Trace 把一次 Agent 运行的时间拆到模型、工具、检索、队列、串行依赖五类，算出各自占比，定位真正的瓶颈。

---

## 1. 阅读前术语表

| 术语 | 说明 |
|---|---|
| Trace | 一次端到端运行的所有 span 组成的树 |
| Span | 一个带起止时间、属性（token、耗时、模型名）的操作单元 |
| Self-time（自身耗时） | span 总时长减去所有子 span 时长，是「这个操作本身」花的 |
| 关键路径（Critical Path） | trace 里决定总时长的最长串行依赖链 |
| TTFT / TPOT | 首 token 时间 / 每输出 token 时间（模型调用拆两段） |
| 队列等待（Queue Wait） | 请求在并发槽、限流、背压里排队的时间 |
| 串行依赖（Serial Dependency） | 下一步必须等上一步完成后才能开始 → 空闲等待 |

---

## 2. 为什么先做 Trace

优化 Agent 最常见的错误是**凭直觉优化模型**（换更快的模型、量化）。但端到端延迟可能根本不在模型——可能在工具慢、检索重复、或大量空闲等待。Trace 的作用是**用数据说话**：把时间占比算出来，才知道该优化哪一层（对应文档 03 的分层优化）。

---

## 3. 五类时间怎么拆

一次 Agent 运行的总墙钟时间，拆成五类：

| 类别 | 是什么 | 典型 span | 关键属性 |
|---|---|---|---|
| **模型** | LLM 推理时间 | `llm.completion` | TTFT、TPOT、输入/输出 token 数 |
| **工具** | 外部工具执行时间 | `tool.call` | 工具名、参数、返回大小 |
| **检索** | 向量检索时间 | `retrieval.search` | query、top-k、embedding 耗时 |
| **队列** | 等并发槽/限流/背压 | `queue.wait` | 等待时长、限流状态 |
| **串行依赖** | 等上一步完成才能开始 | 相邻 span 的**间隙** | gap = 下 span 开始 − 上 span 结束 |

**关键洞察**：前四类是「active span 的耗时」，串行依赖是「span 之间的**空档**」——它不算在任何操作里，却常常是最大头。比如模型吐完最后一个 token、到工具调用发起之间，有编排/序列化/上下文拼装的等待；工具返回后、到下一次模型调用之间，有结果解析和 prompt 重组的等待。

---

## 4. 怎么算时间占比

1. **埋点**：给每个关键步骤打 span（模型/工具/检索/队列各一个类别标签），记录起止时间与 token 属性。工具：OpenTelemetry + Langfuse/LangSmith 这类可观测后端。
2. **算 self-time**：`self_time(span) = duration − Σ child_durations`，把「这个操作自己」和「它调用的子操作」分开。
3. **算间隙**：把同一 trace 内按时间排序的 span 之间没有覆盖的部分累加，就是串行依赖/空闲时间。
4. **归类汇总**：把每类 span 的 self-time（模型还要拆 TTFT + TPOT）汇总，除以总墙钟，得到占比。

```text
总墙钟 = Σ 模型 self-time + Σ 工具 self-time + Σ 检索 self-time
        + Σ 队列 self-time + Σ 串行依赖间隙
```

---

## 5. 五类瓶颈各自的信号与对策

| 主导瓶颈 | Trace 信号 | 下一步（对应文档） |
|---|---|---|
| **模型** | 模型 self-time 占比高、输出 token 巨大 | 上下文压缩/减 token（文档 03）、换档/量化（13-w/05）、提前终止 |
| **工具** | 单个 `tool.call` 极慢、或工具被反复调 | 缓存工具结果、并行无依赖工具（文档 03）、换更快工具 |
| **检索** | 检索 self-time 高、且同一 query 反复出现 | 检索去重/缓存、缩短上下文免重复检索（文档 02/03） |
| **队列** | `queue.wait` 长 | 提高并发、加实例、错峰、预算内并行 |
| **串行依赖** | 间隙占比高（常 >30%） | 并行化无依赖步骤、合并多次小调用、预取 |

**经验判断**：健康的 Agent 里，模型和工具应占大头、串行依赖应在 10–20% 以下；如果间隙 >30%，先解决编排层的串行等待，比优化模型收益大得多。

---

## 6. 一个可复现的测量口径

- **固定负载**：同一批任务、同一模型版本、同一工具/检索后端；
- **每步都记**：token（输入/输出/缓存命中）、TTFT、TPOT、工具耗时、检索耗时、队列等待；
- **多 trial 取分布**：报告 P50/P95 而非单点（尾延迟才是用户体感）；
- **输出三张图**：① 时间占比堆叠、② 关键路径 Gantt、③ 每类随步骤数的增长曲线。

只有把「时间占比 + 关键路径」都摆出来，才能回答「钱和秒都花在哪了」——这是第 14 周编码实验「优化前基线」的第一步。

---

## 7. 本文结论

Trace 的核心价值是把「慢」从感觉变成**可归因的占比**：模型、工具、检索、队列是 active 耗时，串行依赖是 span 之间的**空档**，后者常被忽视却可能是最大头。算出五类占比后，优化才有靶子——串行依赖靠并行/合并，模型靠减 token/换档，工具/检索靠缓存/去重。**先诊断、再优化**，而不是先换模型。
