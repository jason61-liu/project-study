# Agent 无效模式：上下文膨胀、重复检索、无效反思与多 Agent 重复调用

> 目标：把 Agent 系统里最常见的四类「无效步骤」讲清——各自的成因、代价、在 Trace 里怎么识别、怎么治。它们共享一个根因：**做了不该做的重复工作，或把无关信息反复塞给模型**。

---

## 1. 阅读前术语表

| 术语 | 说明 |
|---|---|
| 上下文膨胀（Context Bloat） | 每轮把完整历史、工具输出、检索原文全部重发给模型 |
| 丢失在中间（Lost in the Middle） | 长上下文中模型对中段信息的注意力衰减 |
| 重复检索 | 相同/相近 query 被多次 embedding 与搜索 |
| 无效反思（Ineffective Reflection） | 反思循环不收敛、不带来输出改进 |
| 多 Agent 重复调用 | 多个子 agent 做重叠工作、重复调同一工具 |
| 幂等（Idempotent） | 同一调用多次执行结果一致、可安全去重 |

---

## 2. 上下文膨胀

**是什么**：多轮对话里，每轮都把**全部历史**（用户消息、模型回复、工具输出、检索原文、反思文本）拼进 prompt 重新发给模型。上下文随轮次线性甚至超线性增长。

**代价**：① token 成本随轮次平方级涨（每轮重发所有历史）；② 延迟上升（输入越长 prefill 越慢）；③ **注意力稀释**——重要信息被淹没，模型开始「忘掉」早期约束；④ 可能顶到上下文窗口上限或把 prompt cache 挤出（KV 复用失效，见 12-w/02、03）。

**Trace 里怎么识别**：输入 token 数随轮次单调增长、且缓存命中率下降；总 token 中「历史重发」占比高。

**怎么治**：**上下文选择/压缩**（文档 03）——只保留当前任务相关的历史、把工具输出压缩成摘要、把检索原文替换为引用片段、丢弃失败尝试的中间过程。目标不是「装更多」，而是「少发无关」。

---

## 3. 重复检索

**是什么**：同一（或语义几乎相同的）query 被反复 embedding + 搜索——比如每轮都重新检索同一段背景，或多个 agent 各自检索同一主题。

**代价**：① 检索延迟累积；② embedding 与向量库成本；③ **更隐蔽的危害**：向量检索常带随机性/召回抖动，重复检索可能返回**不同结果**，导致 Agent 依据不一致的证据做判断 → 输出不稳定。

**Trace 里怎么识别**：`retrieval.search` span 的 query 高度相似、或同一证据块被多次拉取。

**怎么治**：① **检索去重/缓存**——按 query 归一化后的 hash 缓存检索结果，同 query 只搜一次；② **证据跨轮复用**——把已检索到的证据存进会话级缓存，后续轮次直接引用，不再重搜；③ 只在「确有新信息需求」时才触发检索。

---

## 4. 无效反思

**是什么**：让模型「自我批评再改一版」，但反思循环**不收敛**——critic 反复说「再改进」，输出却无明显提升，甚至越改越差；或者在没有可验证信号时也做反思（纯凭感觉批评）。

**代价**：反思每轮都是一次完整模型调用（token + 延迟），N 轮反思 = N 倍成本；且无信息的反思会引入噪声、动摇原本正确的答案。

**Trace 里怎么识别**：连续的「critic → revise」span 对，且 revise 后的输出与上一版几乎无 diff，或评测分数不升反降。

**怎么治**：① **有界反思**——反思最多 N 轮，或用「改进幅度阈值」早停；② **有信号才反思**——只在有可验证的反馈（测试结果、检索到的反例、工具报错）时反思，不空谈；③ **提前终止**（文档 03）——检测到循环/不收敛就停。

---

## 5. 多 Agent 重复调用

**是什么**：多个子 agent（或并行子任务）做**重叠的工作**——两个 agent 各自查同一个 API、重新爬同一页、各自读同一份文件，没有共享中间结果。

**代价**：重复的工具调用成本与延迟；结果可能不一致（各自拿到不同版本）；编排层因等待冗余工作而拉长关键路径。

**Trace 里怎么识别**：跨 agent 的 `tool.call` span 参数相同/目标相同，但由不同 agent 分别发起。

**怎么治**：① **编排层去重**——orchestrator 在派活前检查「这个子任务是否已被别人做过」，共享结果；② **共享 scratchpad/记忆**——子 agent 把中间结果写进共享空间，其他 agent 先查再算；③ **幂等工具调用 + 结果缓存**——同一输入的工具调用直接命中缓存，不再真的执行。

---

## 6. 四类无效模式的对照

| 无效模式 | 根因 | 主要代价 | Trace 信号 | 治法 |
|---|---|---|---|---|
| 上下文膨胀 | 历史全量重发 | token 成本、延迟、注意力稀释 | 输入 token 随轮次涨、缓存命中降 | 上下文选择/压缩 |
| 重复检索 | 无缓存、无去重 | 检索延迟、结果抖动 | 相似 query 重复出现 | 检索缓存/去重、证据复用 |
| 无效反思 | 无信号空反思 | N 倍模型调用 | critic→revise 无 diff | 有界反思、有信号才反思 |
| 多 Agent 重复调用 | 无共享中间结果 | 重复工具成本、不一致 | 跨 agent 相同工具调用 | 编排去重、共享 scratchpad |

共同根因一句话：**这些浪费都来自「重复」——重复发历史、重复检索、重复反思、重复调用**。诊断靠 Trace（文档 01），治理靠分层优化（文档 03）。

---

## 7. 本文结论

四类无效模式是 Agent 系统「无效步骤」的四大来源，它们的共同特征是**重复**：重发历史（上下文膨胀）、重查证据（重复检索）、重想一遍（无效反思）、重做一遍（多 Agent 重复调用）。识别它们靠 Trace 里的三类信号——输入 token 增长、相似 span 重复、输出无 diff；治理它们的统一思路是**去重 + 复用 + 有界**。第 14 周编码实验的「上下文去重/压缩、循环检测、提前终止」正是针对这四类的落地。
