# Speculative Decoding 的 Draft/Verify/接受率，与 Prefix/Prompt Cache、语义缓存、结果缓存的正确性边界

> 目标：两件事——(1) 讲清推测解码（Speculative Decoding）的 Draft→Verify→接受/拒绝三阶段、接受率如何决定收益，以及它为什么**保分布**却**不省吞吐**；(2) 严格区分三种「缓存」的正确性边界：哪些缓存是无损的、哪些只是近似、哪些在什么条件下会返回错误答案。

---

## 1. 阅读前术语表

| 术语 | 说明 |
|---|---|
| Draft 模型 | 小/快的模型，先自回归地猜一串 token |
| Target 模型 | 大/慢的正式模型，负责验证和最终采样 |
| Verify（并行验证） | target 一次前向并行检查整串 draft token |
| 接受率 α | draft token 被 target 采纳的比例 |
| 修正拒绝采样 | 用「拒绝/重采样」保证输出分布与 target 完全一致 |
| 自回归瓶颈 | 逐 token 生成导致每步只能串行一次前向 |
| Prefix/Prompt Cache | 精确 token 前缀命中 → 复用 KV Cache |
| 语义缓存 | 按 embedding 相似度复用「语义相近」的历史回答 |
| 结果缓存 | 完整 prompt 精确匹配 → 直接返回缓存的输出 |

---

## 2. Speculative Decoding：为什么要「猜」

自回归生成的瓶颈是**串行**：每生成一个 token，都要等一次 target 前向。而一次前向**并行算 γ 个 token 的 logits** 几乎和算 1 个一样贵——所以「串行 1 个」是巨大的浪费。推测解码的思路：**让一个便宜的 draft 模型先串行猜 γ 个 token，target 再一次性并行验证这 γ 个**。

---

## 3. 三阶段：Draft → Verify → 接受/拒绝

1. **Draft**：draft 模型（小模型、或 DeepSeek-V3 的 MTP 头、或 Medusa 头）自回归生成 γ 个候选 token；
2. **Verify**：target 模型把 `[prefix + γ 个候选]` 一起喂进一次前向，并行拿到每个位置的 target 概率 `p(x)` 和 draft 概率 `q(x)`；
3. **接受/拒绝（修正拒绝采样）**：对每个位置 i，抽一个均匀随机数 u，若 `p(x_i)/q(x_i) ≥ u` 则**接受**该 token，否则**拒绝**并从 `max(0, p(x) − q(x))` 重新采样一个 token，之后丢弃后续 draft token。

**关键性质——保分布**：修正拒绝采样保证最终生成的序列分布**与 target 模型自回归采样完全一致**，不是「近似」而是「精确等价」。这是推测解码能广泛使用的前提：它只改变速度，不改变模型行为。

---

## 4. 接受率如何决定收益

设 draft 接受率为 α、每次猜 γ 个 token，则**平均每步生成的 token 数**为：

```text
(1 − α^(γ+1)) / (1 − α)
```

- α 高（如 0.7–0.9）→ 一步接近 γ 个，大幅减少 target 前向次数；
- α 低（如 0.3）→ 大部分 draft 被拒，收益趋近于零甚至为负（多了 draft 的开销）。

**收益是「延迟」不是「吞吐」**：

| 维度 | 推测解码的影响 |
|---|---|
| 延迟（TTFT/TPOT 的单步墙钟） | **下降**：target 串行前向次数变少 |
| 吞吐（token/s） | **不升反降**：总 FLOPs = target 验证 + draft 生成 ≥ 原来，还多了 draft 开销 |
| 分布 | **不变**（修正拒绝采样保分布） |

**划算条件**：① 接受率高（draft 和 target 输出高度一致，比如同一家族的 MTP 头）；② draft 比 target 便宜一个数量级（否则 draft 自己就慢，省不掉）。DeepSeek-V3 用 MTP 头做 draft（文档 02）就是同时满足两条的典型。**风险**：draft 不匹配时白算、显存/内存多占一份 draft 模型。

---

## 5. 三种缓存的正确性边界（本讲重点）

「缓存」不是铁板一块，三种缓存的**正确性保证完全不同**。区分标准是：**「被复用的东西」是不是「当前 prompt 的确定函数」**。

| | 命中条件 | 复用什么 | 正确性 | 何时会错 |
|---|---|---|---|---|
| **Prefix/Prompt Cache** | 精确 token 前缀匹配 | KV Cache | **无损** | 不会错（见下） |
| **语义缓存** | embedding 相似度超阈值 | 相近问题的历史回答 | **近似，可能错** | 相似 ≠ 等价 |
| **结果缓存** | 完整 prompt 精确匹配 | 缓存输出 | **条件正确** | 非确定性 / 依赖外部状态 |

### 5.1 Prefix/Prompt Cache：无损

命中条件是最严格的**精确 token 前缀匹配**（vLLM 按 block、SGLang 按 token 对齐）。复用的是 KV Cache——因为「同一模型 + 同一前缀」算出的 KV 是**确定性的**，所以复用的 KV 和重新 prefill 算出来的**完全一致**，不引入任何误差。正确性边界很清晰：**只对「字面完全相同的前缀」生效**，多一点少一点 token 都不命中（或只能命中到最长公共前缀）。它省的是 prefill 计算，不改变输出。

### 5.2 语义缓存：近似，可能错

命中条件松——按 embedding 相似度找「意思相近」的历史问题，直接复用它的回答。**正确性风险**：相似度是启发式，「语义相近」不保证「答案相同」。两个措辞相似但**隐含参数不同**的问题（「上海明天天气」vs「上海后天天气」）可能被判为命中，返回**错误答案**。因此语义缓存只适合**对改写不敏感、答案可复用**的场景（如 FAQ、通用解释），**绝不用于事实性、参数化、有时效的查询**。

### 5.3 结果缓存：条件正确

命中条件是完整 prompt 精确匹配。它只在**「输出是 prompt 的纯函数」**时正确：

- ✅ 安全：`temperature=0` + 固定 seed + 无外部依赖的确定性生成；
- ❌ 会错：① `temperature>0`（非确定性，重跑答案不同）；② 答案依赖**可变外部状态**（当前时间、实时数据、用户个性化上下文）；③ 涉及有副作用的工具调用（不该被缓存跳过）。

正确性边界一句话：**结果缓存的前提是「同 prompt ⇒ 同输出」，一旦模型非确定或答案依赖 prompt 之外的时空状态，缓存就失效甚至有害**。

---

## 6. 本文结论

- **推测解码**：Draft 串行猜 → Verify 并行验 → 修正拒绝采样接受/重采样。它**精确保分布**（输出与 target 自回归一致），**只省延迟不省吞吐**（总 FLOPs 不减反增）。收益由接受率 α 决定，划算条件是「接受率高 + draft 足够便宜」。
- **三种缓存的正确性边界**：Prefix/Prompt Cache 是**无损**的（精确前缀 + 确定性 KV）；语义缓存是**近似**的（相似度 ≠ 等价，会返回错误答案）；结果缓存是**条件正确**的（只在确定性 + 无外部依赖时安全）。
- **统一判据**：问「被复用的东西是不是当前 prompt 的确定函数」——KV 是（无损）、回答的语义是近似（可能错）、完整输出只有在确定且无状态时才可能是。
