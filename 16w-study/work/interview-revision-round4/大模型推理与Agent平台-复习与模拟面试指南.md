# 大模型推理与 Agent 平台：复习与模拟面试指南

> 配套题库：[大模型推理与 Agent 平台及应用开发：157 道面试题库](大模型推理与Agent平台-面试题库150题.md)  
> 使用目标：把“看懂答案”转化为“能在限定时间内讲清机制、工程闭环与边界”。

---

## 一、作答标准

不要背固定指标，也不要只复述名词。每个回答至少闭合下面五件事：

1. **结论**：先回答选什么、为什么，避免从背景知识讲起。
2. **机制**：说明数据、状态或请求如何流动，关键组件分别做什么。
3. **工程实现**：落到接口、状态、存储、并发、权限、失败处理和观测信号。
4. **边界与权衡**：指出方案何时失效、代价是什么、有哪些替代方案。
5. **验证方法**：给出实验、压测、故障注入或评测集，而不是编造“行业标准数字”。

### 三种时间尺度

| 时间 | 推荐结构 | 合格标准 |
| --- | --- | --- |
| 30 秒 | 结论 → 核心机制 → 一个边界 | 能回答“是什么、为什么”，不堆名词 |
| 2 分钟 | 结论 → 机制 → 工程落点 → 失败模式 → 验证 | 能体现做过系统，而不只是读过文档 |
| 10 分钟以上 | 需求约束 → 架构 → 主流程 → 状态与副作用 → 安全可靠性 → 容量与评测 → 权衡 | 架构图和流程图能与口述逐项对应 |

综合设计题应先画组件与信任边界，再画成功路径和至少一条失败/恢复路径。图中每个存储、队列和外部副作用都要说明 owner、持久化时机、幂等语义与观测字段。

## 二、必须统一的术语

| 术语组 | 面试中应明确的区别 |
| --- | --- |
| Agent Loop / Runtime（Harness） | 模型负责产生决策；Runtime 负责执行、预算、超时、重试、权限、状态和终止 |
| Runtime State / Checkpoint / 长期记忆 / 业务数据库 | 当前运行状态、可恢复快照、跨会话知识、业务事实是四种不同生命周期的数据 |
| Function Calling / MCP / A2A | 模型输出工具调用、客户端与工具服务器协议、Agent 间协作协议，不是同一抽象层 |
| `request_id` / `trace_id` / `idempotency_key` / `effect_id` | 请求实例、链路追踪、稳定业务意图、外部副作用实例，不能相互替代 |
| Workflow / Agent | 固定控制流强调确定性；Agent 强调模型参与动态决策，可在工作流节点内使用 Agent |
| Manager / Handoff | Manager 保留控制权并调用子 Agent；Handoff 转移当前会话或任务控制权 |
| KV Cache / Prefix Cache / Checkpoint | 单序列注意力状态、跨请求稳定前缀复用、应用运行状态恢复，解决的问题不同 |
| Prefill / Decode | 前者并行处理输入且偏算力；后者逐 token 生成且更受内存带宽和调度影响 |
| TTFT / TPOT（ITL）/ Throughput / Goodput | 首 token 延迟、token 间隔、总吞吐、满足 SLO 的有效吞吐 |
| MHA / GQA / MLA | 完整多头 KV、分组共享 KV、低秩潜变量压缩；质量、显存和内核复杂度不同 |
| TP / PP / EP | 张量、流水线、专家并行；通信模式、负载均衡和容错边界不同 |

## 三、按面试轮次复习

### 一面：原理和机制

目标是准确解释“为什么”，并能完成小规模推导或伪代码。优先题目：

- Agent 与工具：1–9、13–20、22–25；
- RAG 与记忆：29–40、42–45；
- Runtime 与评测：62–69、72–79；
- 推理基础：106–114、116–123、133–140。

作答时重点检查：是否混淆模型能力与 Runtime 能力；是否只说组件名称而没有状态流；公式中的变量、单位和假设是否完整。

### 二面：工程设计和故障诊断

目标是把机制落到生产约束，并能从症状定位责任层。优先题目：

- 工具平台与 RAG：17、20、23–28、32–46；
- 编排、恢复与框架：49–61、64–71；
- 评测、安全和可靠性：74–81、83–105；
- Serving 工程：115、119–132、138–144。

每题至少补齐四个追问：失败发生在哪里、状态保存在哪里、重复执行会怎样、如何证明修复有效。

### 系统设计轮：端到端闭环

重点题目：13、28、46、61、71、81、93、105、115、132、144–149、151、154、157。回答时按以下顺序展开：

1. 澄清用户、流量、延迟、数据敏感度和一致性目标；
2. 画架构图，标明控制面、数据面、信任边界和外部依赖；
3. 画主流程与失败恢复流程，明确状态转换；
4. 解释权限、幂等、取消、回放、降级和容量模型；
5. 给出离线评测、线上指标、告警和发布门禁；
6. 最后比较备选方案，不把框架名称当作设计结论。

## 四、三套模拟面试

### 模拟一：一面基础机制（60 分钟）

从下列题目中随机抽 10 题，每题先用 30 秒回答，再任选 3 题展开到 2 分钟：3、14、20、30、40、49、62、69、73、82、94、106、108、109、116、117、123、133、134、137。

通过标准：结论明确；术语无混淆；至少能说出一个反例或适用边界；推导题不跳步。

### 模拟二：二面工程深挖（90 分钟）

从下列题目中随机抽 8 题，每题允许连续追问：9、17、25、34、38、45、51、55、60、74、77、86、87、90、99、100、103、104、121、124、125、127、130、131、138、140。

统一追问：数据写到哪里？谁拥有状态？超时后是否仍可能产生副作用？怎样回放？租户边界在哪里？上线前用什么证据验收？

### 模拟三：系统设计（120 分钟）

从 61、93、105、132、145、148、151、154、157 中随机抽 2 题。每题 10 分钟澄清和画图、30 分钟讲解、20 分钟追问。

通过标准：

- 架构图、流程图与口述使用相同的组件和状态名称；
- 正常路径、失败路径、恢复路径完整；
- 模型、检索、工具、编排和基础设施问题能够分层归因；
- 安全、可靠性、成本和效果都有可验证闭环；
- 对不确定的版本能力明确说“需验证”，不把经验值包装成协议事实。

## 六、版本敏感内容复核清单

以下内容变化快，面试前应重新查看官方文档；题库只保留稳定机制，不把某一版本实现写成永久事实。

- **MCP**：初始化、能力协商、通知和连接关闭语义；尤其不要虚构协议未定义的关闭消息。参考 [MCP Lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)。
- **A2A**：Agent Card、Task/Message/Artifact、流式与推送、认证授权等字段和版本。参考 [A2A Protocol Specification](https://a2a-protocol.org/latest/specification/)。
- **LangGraph**：Checkpoint、Thread、状态迁移及已部署图升级后的兼容性。参考 [LangGraph Backwards Compatibility](https://docs.langchain.com/oss/python/langgraph/backward-compatibility)。
- **OpenAI Agents SDK**：Runner 循环、Session、RunState、Guardrail、Handoff、Tracing 与长任务恢复集成。参考 [Running Agents](https://openai.github.io/openai-agents-python/running_agents/)。
- **推理引擎**：调度策略、Chunked Prefill 默认值、量化后端、Prefix Cache、并行方式和硬件支持矩阵。
- **模型架构/API**：上下文长度、reasoning effort、reasoning token 的可见性/计费/缓存、工具调用事件和多模态限制。

复核记录建议只写四项：`检查日期`、`官方来源`、`变化点`、`影响题号`。无法确认时使用“当前版本文档显示……”的限定表达。
