# 技术与业务报告

## 摘要与上线结论

项目解决“从多份授权材料中检索证据、识别冲突、生成可核验引用草稿”的任务。人工假设基线为 30 分钟/任务、一次通过率 90%、升级率 10%、人工成本 US$20/任务；这些不是实测。当前技术基线在合成任务上可重复，但缺少真实业务样本，因此结论仍是“有限上线”：只生成草稿，不自动发布，高风险请求必须人工审批。

## 消融决策

1. 架构：双路代理重复执行并要求结果一致，质量未变，成本 2 倍，延迟约增加 58%。没有证据支持多 Agent，维持单工作流。
2. 上下文：固定字符硬截断让证据支持率归零。压缩不能仅看 Token/成本，必须按关键事实保留率和业务成功率设 Gate。
3. 模型/路由代理：当前没有真实模型；以“自动抽取”和“风险送人审”作为路由边界实验。40% 升级换来风险任务不自动完成，正式模型路由仍待真实模型快照验证。
4. 关键优化：10 倍重复输入经内容/URL 去重后成本不变，延迟影响很小，证明在这组规模下去重有效。

## 标准 Benchmark 子集

复用第 8 周保存的官方 tau3 `banking_knowledge` v1.0.1 五题原始 JSON 和 provenance，重新运行统一 Harness、Trace 与 `actions_match` Grader，结果 5/5。执行 Agent 明确接收 Gold Actions，因此该实验只证明版本化任务适配和评分合同可执行，不证明研究 Agent 能解决多轮银行任务，也不可横向比较官方榜单。相较业务集，它覆盖政策约束和标准动作合同，却不覆盖本项目的引用充分性、租户隔离、审批、恢复和成本门槛；这些由本地业务与安全集补充。

## 失败、定位与修复

最重要的评测失败发生在上下文消融：最初 Grader 在整份报告中查找主题，问题原文也包含主题，导致证据即使被截断仍误判成功。修复是只在 Evidence excerpt 中验证主题，再重跑，成功率从错误的 100% 修正为 0%。这说明 Outcome/证据 Grader 必须检查权威对象，不能被最终文本或输入回显欺骗。

已复现并处理的系统故障包括重复投递、陈旧写、进程重启、审批暂停、空检索、非法请求、数据库锁、Sandbox 超时、Worker 中断和费用终止。仍未覆盖多区域分区、真实供应商限流和强隔离 Sandbox 崩溃。

## 身份与治理

网关完成 OAuth/OIDC 签名校验后，参考 PEP 再检查 issuer、audience、expiry、scope 和撤销状态；原始凭证不进入模型、Trace 或持久状态。RBAC 表达角色，ABAC 绑定租户、资源和风险，审批不能跨租户。记忆只接收经审批且带 provenance 的事实，支持版本更新、导出、删除和污染拒绝；缓存键包含租户。

## 发布与回滚

流水线顺序是测试 → 业务 Eval Gate → 安全/故障硬门槛 → Shadow → 5% Canary → 扩量。演练先复现一个离线成功率 94% 的候选被 CI 阻断；另一个离线 99% 的候选通过 Shadow 后，在 5% Canary 观察到 94% 而自动回滚。活动版本保持 `research-agent-v1`，手工回滚路径也独立验证。安全失败没有错误预算，任一跨租户、未审批执行或无效引用都立即回滚。

## 业务收益验证与下一步

模拟反馈中 Offline Eval 从 90% 升至 96%，Online KPI 从 86% 升至 96%，方向一致；它只证明闭环计算正确，不证明真实收益。下一步收集 200 个脱敏影子任务，双人标注并保留固定 holdout；比较耗时、一次通过率、人工升级率、错误成本和单位成功任务成本。达到目标且安全硬门槛为零后，才考虑扩大 Canary。
