## 2. 无笔记口述：Tokens/s 更高为什么不一定意味着用户体验更好

下面是一段约 90 秒、可以脱离笔记直接回答的版本：

> Tokens/s 是一个**系统吞吐**指标，用户体验是一个**单请求延迟**指标，两者由 Little's Law 相连，但不是一回事。吞吐高，可能是因为系统把很多请求的 Decode 步骤批处理在一起、共享一次权重读取；这摊薄了硬件成本，但单个请求仍然要经历客户端排队、网络、服务端排队、Prefill 和逐 token 的 Decode。
>
> 第一，吞吐和延迟经常此消彼长。为了把吞吐做高，服务端会增大 batch、开启连续批处理和 Chunked Prefill，结果单个请求可能要等更久才能抢到 Prefill 槽，TTFT 反而上升。用户感知的是 TTFT 和端到端延迟，不是系统每秒产出了多少 token。
>
> 第二，吞吐可能是「浪费出来的」。如果系统大量重试、疯狂产出无效 token、任务反复失败，Throughput 可以很高，但用户拿到的有效结果没变多——这就是 Goodput 和 Throughput 的区别。一个高吞吐低成功率的系统，用户体感是「很快，但老是重来」。
>
> 第三，吞吐高只说明「平均」能扛得多，不代表「尾部」用户不慢。高并发下 P99 可能比均值高数倍，多数用户很快，少数用户卡在排队里，而吞吐数字完全看不出这个尾巴。

数学上，吞吐由 `Concurrency = λ × W` 约束：并发固定时，延迟 `W` 上升，吞吐 `λ` 反而下降；吞吐的上升必须靠提高并发，而提高并发又抬高尾延迟。本周实测就印证了这一点：并发从 1 提到 16，吞吐从 794 涨到 6690 tokens/s，但端到端 P95 从 324ms 涨到 613ms。所以「Tokens/s 高」是系统在**某个并发、某个延迟、某个成功率下的平衡结果**，不是独立的用户体验指标。

## 3. 推理性能面试题与参考答案

以下 12 道题按「先明确口径和目标，再给机制，最后说明权衡与失败模式」的方式回答。只报名词、不落到时间轴或容量边界，不算完整答案。

### 题 1：解释 TTFT、TPOT 和端到端延迟的区别

**参考答案：**三个指标是**同一条流式时间轴上的不同区间**，不是并列的 KPI。TTFT 是从请求发出到第一个 token 出现，TPOT 是相邻两个输出 token 之间的平均间隔，端到端延迟是到最后一个 token（或完成）的时间。三者满足 `E2E ≈ TTFT + (N-1)×TPOT + 收尾`。要优化 E2E，只能三选一或组合：缩短 TTFT、缩短 TPOT、减少输出 token 数 N。

### 题 2：为什么 Prefill 主导 TTFT，而 Decode 主导 TPOT？

**参考答案：**Prefill 要把全部输入 token 并行编码，是计算受限的，时间近似线性于输入 token 数，所以长 prompt 直接抬高 TTFT。Decode 是自回归的，每生成一个 token 都要读一遍 KV 和权重，是内存带宽受限的，单 token 时间 `TPOT ≈ 权重字节数 ÷ 内存带宽`，几乎不随输入/输出内容变化。本周长度扫描实测：输入 256→4096 时 TTFT 从 5.5ms 升到 81ms，而 TPOT 稳定在 ~1.13ms 不变——正是这个机制。

### 题 3：一次慢请求怎么定位是客户端、网络、服务端、模型还是工具的问题？

**参考答案：**把端到端拆成六个 Span 各打一个时间戳：`client.wait`（客户端发起→发送）、`http.request`（发送→服务端收到）、`server.queue`（收到→Prefill 开始）、`gen_ai.prefill`、`gen_ai.decode`、`tool.execute`。关键陷阱是**客户端排队发生在请求到达服务端之前**，服务端 Trace 看不到，必须从客户端发起处打点。有了这六段，任何慢请求都能立刻归因到具体归属，而不是互相甩锅。

### 题 4：并发提高时，吞吐和尾延迟怎么变？为什么？

**参考答案：**吞吐先随并发近似线性上升，接近饱和点后走平甚至回落；尾延迟（P95/P99）低并发时贴近均值，高并发时陡增。机制是有限资源（GPU 计算、KV 带宽、连接池）上的排队：并发超过能力后，多余请求只能排队，`L = λW` 决定了延迟上升反过来抑制吞吐。本周并发扫描：并发 1/4/16 时吞吐 794/3282/6690 tokens/s，但 P95 从 324ms 跳到 613ms，且 `decode_peak` 封顶在 8——说明 16 个在途请求已经在 8 个 Decode 槽上排队。

### 题 5：流式响应改变了什么，没改变什么？

**参考答案：**流式把「等待」从「空白」变成「打字机」，显著降低**感知的 TTFT**，但**不改变端到端延迟、总 token 数、吞吐和成本**。两个测量陷阱：一是只测 TTFT 就说「延迟降低了」，但需要完整结果的任务端到端没变；二是把「首 token 快」当「任务快」，对需要函数调用完成才能继续的 Agent 步骤，流式收益有限。Benchmark 必须同时报流式与非流式，并区分「用户体验延迟」和「任务完成延迟」。

### 题 6：速率限制（RPM/TPM）如何污染 Benchmark？

**参考答案：**限流生效时系统返回 429 或把请求排队，会造成四类失真：吞吐被削平（测到的是配额不是能力）、尾延迟出现由重试/排队造成的假长尾、重试放大让到达率翻倍再触发限流形成正反馈、以及被 429 拒掉但已计费的请求污染成本。RPM 约束事务吞吐、TPM 约束 token 吞吐，长输出负载往往先击穿 TPM。测量时要分开「受配额约束」和「受硬件约束」的吞吐，报告中单独标注是否触发限流。

### 题 7：为什么 Benchmark 必须有 Warm-up 和固定数据集？

**参考答案：**Warm-up 排除冷启动（模型加载、前缀缓存未命中、连接池/线程池冷启动、GPU 频率爬坡），否则前几次测量把冷启动当成稳态性能；预热样本必须丢弃并记录策略。固定数据集是为了可复现：输入长度分布、内容难度、缓存命中率都影响结果，随机 prompt 不可比；数据集要版本化、覆盖代表性负载、与评测集解耦。

### 题 8：为什么单次调用和均值都不够？P95/P99 为什么需要更多样本？

**参考答案：**LLM 推理有大量跨 Trial 的非确定性（浮点、调度、硬件温度、供应商共享集群），单次调用是「噪声的一次实现」。延迟分布几乎从不正态，均值会被尾部异常值污染，P95/P99 才反映「多数用户最坏遇到什么」。而 P95/P99 只依赖分布尾部的一小部分样本，需要比均值多得多的样本量才有意义——均值的置信区间宽度随 `√n` 缩小，但百分位的区间要用 bootstrap、且需要数百次 Trial 才能估准 P99。

### 题 9：Little's Law 怎么用于容量估算？

**参考答案：**稳态下 `L = λW`（在途数 = 吞吐率 × 平均停留时间）。两个方向：从负载推并发——已知目标吞吐和测得延迟，`L = λ_target × W_p95` 就是需要的并发槽，再乘重试放大和余量；从并发推吞吐上限——`λ_max = L_max / W`。它是 Benchmark 的「出口」，把「测到的延迟分布」和「可承受的并发」翻译成「能承诺的吞吐与服务等级」。

### 题 10：单位成功任务成本和单次 token 费用有什么区别？怎么算？

**参考答案：**单次 token 费用不分成功失败、不看重试、不含工具/基础设施、把调用当任务，是错误的分母。单位成功任务成本 = `(模型 + 工具 + 基础设施 + 重试放大) ÷ 成功逻辑任务数`。近似等价于 `每次 Attempt 成本 ÷ 成功率`，拆成两个独立杠杆：降低单次成本、提高成功率。重试放大 `A = 1+p+p²+…` 只作用在分子上，不增加分母。本周 Agent 实测：budget 从 100 提到 300，成功率 80%→100%、重试放大从 2.10 降到 1.00，单位成功成本从 1737.75 降到 962 µUSD；再往 500 提，成本又因每成功 token 变多涨回 1262——甜点不在最高质量，而在成功率和单次成本的交点。

### 题 11：Goodput 和 Throughput 的区别？

**参考答案：**Throughput 数的是「产出了多少 token/请求」，Goodput 数的是「产出了多少**有用**的 token/成功任务」。要扣除重试 token、取消/丢弃的请求、被 Guardrail 拒绝的输出、无效中间步骤。系统可以靠大量重试和无效 token 把 Throughput 做高，但用户的单位成本和质量没改善。Goodput 是把「速度」锚定到「价值」的桥梁，报告吞吐不报 Goodput，等于只报营收不报利润。

### 题 12：为什么量化后吞吐提升，不等于所有任务成本都下降？

**参考答案：**量化降低的是**每次 Attempt 的成本**（更少的显存、更快的权重读取），但单位成功任务成本 = 每次成本 ÷ 成功率。如果量化让成功率从 90% 掉到 50%，重试放大把分子顶上去，单位成本反而翻倍。所以量化的收益只在「成功率不掉、或下降被重试放大放大得少」的任务上成立；对高风险、长尾任务，宁可路由到更贵但更准的模型。这正是第 13 周模型路由的出发点。

- **最大卡点：**把「吞吐」和「延迟」放在同一张图上看，而不是各自单独报一个漂亮数字。
